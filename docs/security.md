# Безпека: секрети проєкту

## Що таке секрет

**Секрет** — будь-яке значення, яке дає доступ до сервісу або даних від вашого імені: токени, паролі, ключі API, рядки підключення до бази.

Хто знає секрет, той може діяти як ви: керувати ботом, читати й змінювати базу, витрачати ліміти акаунта. Тому секрет:

- не пишуть у код, README чи інші файли, які потрапляють у Git;
- не публікують у чатах, скріншотах, логах;
- зберігають окремо від коду — у нас це файл `.env`, який є тільки на вашому ПК.

Звичайні налаштування (назва бази, порт, рівень логування) — не секрети: їх можна зберігати в коді.

## Які секрети є у проєкті

| Секрет | Де зберігається | Що дає | Звідки взяти |
|---|---|---|---|
| `BOT_TOKEN` | `.env` | повне керування ботом: читати повідомлення, які йому пишуть, і відповідати від його імені | [@BotFather](https://t.me/BotFather) |
| `DATABASE_URL` | `.env` | повний доступ до бази Neon: читати, змінювати й видаляти всі дані. Містить логін і **пароль** бази | Neon Console → проєкт → **Connect** |
| ngrok authtoken | `C:\Users\<user>\AppData\Local\ngrok\ngrok.yml` — поза проєктом | відкривати тунелі від імені вашого акаунта ngrok | [dashboard.ngrok.com](https://dashboard.ngrok.com/get-started/your-authtoken) |

### Хто які секрети отримує

Кожен сервіс отримує лише ті секрети, без яких не може працювати:

| Сервіс | `BOT_TOKEN` | `DATABASE_URL` | Як передається |
|---|---|---|---|
| `bot` | так | так | `env_file: .env` |
| `migrate` | так (не використовує) | так | `env_file: .env` |
| `api` | **ні** | так | `environment: DATABASE_URL: ${DATABASE_URL}` — лише одна змінна з `.env` |
| `frontend` (React) | **ні** | **ні** | секретів немає взагалі |

```
.env ──(docker compose)──► змінні середовища контейнера ──► os.getenv("BOT_TOKEN"), os.getenv("DATABASE_URL")
```

- Локально без Docker `.env` читає python-dotenv (`load_dotenv()`).
- У Docker image файл `.env` **не потрапляє**: `Dockerfile` копіює лише `app/`, `api/` і міграції, а `.dockerignore` (і `frontend/.dockerignore`) виключає `.env` ще на етапі збирання. Значення передаються контейнеру лише під час запуску.

## Web-адмінка: frontend не знає секретів

**Правило:** React не підключається до Neon напряму. Frontend звертається тільки до backend API, а `DATABASE_URL` знає лише backend.

Чому це важливо: усе, що є у frontend, бачить кожен, хто відкрив сторінку — код JavaScript завантажується в браузер повністю. Якби `DATABASE_URL` був у React, будь-хто міг би скопіювати його й отримати повний доступ до бази.

Як це забезпечено:

| Що | Як |
|---|---|
| React звертається лише до `/api/...` | `frontend/src/api.js`; адресу API знає dev-сервер Vite, а не браузер |
| API повертає лише потрібні поля | схеми відповідей у `api/main.py` (`TransactionOut`, `CarOut`, …) — без `telegram_id`, паролів, службових даних |
| API лише читає | тільки `GET`-запити, жодних змін у базі з адмінки |
| у зібраному JavaScript немає секретів | перевірено: у бандлі немає `postgresql://`, `neon.tech`, `DATABASE_URL`, `BOT_TOKEN` |
| змінні `VITE_*` | потрапляють у браузер — тому туди ніколи не можна класти секрети; зараз використовується лише `VITE_API_BASE_URL` (адреса API, не секрет) |

### Авторизації поки немає

Адмінка й API зараз **без входу за паролем** і показують операції всіх користувачів. Тому вони відкриті **лише на цьому ПК**: порти прив'язані до `127.0.0.1` (`127.0.0.1:8000`, `127.0.0.1:5173`), з інших пристроїв у мережі їх не відкрити.

⚠️ До появи авторизації **не публікуйте адмінку й API в інтернет** (Render, ngrok тощо): будь-хто, хто знає адресу, побачив би всі фінансові дані.

### Зовнішні сервіси

| Сервіс | Що отримує | Чого не отримує |
|---|---|---|
| НБУ (курс $) | лише дату операції | суми, авто, дані користувачів |
| Вікіпедія (фото моделі) | лише марку й модель авто | VIN, суми, дані користувачів |

Обидва — відкриті API без ключів, тож секретів для них не потрібно.

### Що захищає секрети в проєкті

| Захист | Що робить |
|---|---|
| `.gitignore` | `.env` не потрапляє в Git і на GitHub |
| `.dockerignore`, `frontend/.dockerignore` | `.env` не передається в Docker під час збирання образів |
| мінімум секретів у сервісах | API отримує лише `DATABASE_URL`, frontend — жодного секрету |
| порти лише на `127.0.0.1` | API й адмінка недоступні з мережі, поки немає авторизації |
| detect-secrets (`docker compose run --rm secrets-scan`) | перед комітом шукає токени й паролі у файлах Git, включно з нашим плагіном для Telegram-токенів |
| логи без секретів | бот не пише в лог `BOT_TOKEN` і `DATABASE_URL`; користувачі — лише за `user_id` |
| ручна перевірка | `git status` перед комітом: `.env` не повинен бути в списку |

## `.env` і `.env.example`

| | `.env` | `.env.example` |
|---|---|---|
| Що містить | **справжні** значення секретів | назви змінних і заглушки без справжніх значень |
| Для чого | щоб бот працював на вашому ПК | щоб інші (і ви на новому ПК) знали, які змінні потрібні |
| У Git | **ні** — в `.gitignore` | **так** — це документація |
| Хто бачить | тільки ви | усі, хто бачить репозиторій |
| Якщо файлу немає | бот не запуститься: `Не задано BOT_TOKEN` / `Не задано DATABASE_URL` | новій людині незрозуміло, що налаштовувати |

Як із ними працювати:

1. Нова змінна-секрет → додати її **в обидва файли**: у `.env` справжнє значення, у `.env.example` — заглушку й коментар, де її взяти.
2. Новий ПК → `Copy-Item .env.example .env` і вписати справжні значення.
3. У `.env.example` не пишіть навіть «правдоподібних» прикладів — наприклад, рядка підключення з вигаданими логіном і паролем. detect-secrets сприйме це як витік, і правильно: різницю між прикладом і справжнім паролем сканер не бачить. Тому в нас заглушки: `your-telegram-bot-token`, `your-neon-connection-string`.

## Що робити при витоку секрету

Витік — секрет потрапив туди, де його можуть побачити інші: коміт на GitHub, скріншот, повідомлення в чаті, лог.

**Головне правило:** спочатку **відкликати** секрет і створити новий, а вже потім прибирати сліди. Видалення файлу чи коміту не допомагає: секрет міг бути скопійований за секунди після публікації, а в історії Git і кешах він лишається.

### 1. Відкликати секрет і отримати новий

**`BOT_TOKEN`:**

1. [@BotFather](https://t.me/BotFather) → `/mybots` → ваш бот → **API Token** → **Revoke current token**.
2. Старий токен одразу перестає працювати, BotFather видає новий.

**`DATABASE_URL` (пароль бази Neon):**

1. Neon Console → проєкт → роль бази (`neondb_owner`) → **Reset password**.
2. Скопіювати новий рядок підключення через **Connect**.
3. Перевірити дані в базі: чи не з'явилися чужі записи, чи нічого не видалено. За потреби — відновити базу на момент до витоку (Neon зберігає історію змін у межах налаштованого періоду).

**ngrok authtoken:**

1. [dashboard.ngrok.com](https://dashboard.ngrok.com) → **Authtokens** → видалити скомпрометований токен і створити новий.
2. `ngrok config add-authtoken <НОВИЙ_ТОКЕН>`.

### 2. Оновити проєкт

1. Вписати нове значення в `.env`.
2. Перестворити контейнер — `restart` не перечитує `.env`:

   ```powershell
   docker compose up -d --force-recreate
   ```

3. Перевірити логи: `docker compose logs bot` — має бути `База даних готова` і `Run polling for bot @...`.

### 3. Прибрати секрет звідти, де він опинився

- Файл у репозиторії → прибрати секрет із файлу, перенести в `.env`, закомітити.
- Секрет лишається в **історії Git**. Після відкликання він уже нічого не відкриває, тому переписувати історію зазвичай не потрібно. Якщо все ж треба — [інструкція GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository).
- Скріншот, повідомлення в чаті → видалити, де можливо.

### 4. Зробити висновок

Записати, як стався витік, і що змінити, щоб не повторилося: додати правило в `.gitignore`, запускати detect-secrets перед комітом, не вставляти секрети в чати.

## Перевірка перед кожним комітом

```powershell
git status                               # .env і node_modules не повинні бути в списку
docker compose run --rm secrets-scan     # має бути: нових секретів не знайдено
```

У Git не повинні потрапити: `.env`, `DATABASE_URL`, `BOT_TOKEN`, паролі, API-ключі, `node_modules/`.
